## 1. プロダクトの目的と基本方針

本MVP (PoC版) の目的は、顧客 (東明社等) が求める「AIによる自動架電 (督促等)・受電と、その結果のロギング・次アクション (人間による再架電) の要否判定」の業務適合性を検証することです。

納期 (2026年5月中旬) を厳守するため、リッチなUI開発はフェーズ2以降に見送り、「OpenAI Realtime API + 既存のFirestore/スプレッドシート連携基盤 + 最低限のReact UI」を組み合わせた最速構成で構築します。

リッチな管理画面 (ノードベースのコールフロー、ファイルアップロードRAG、CRM連携、有人転送など) は本開発フェーズに送り、PoCでは検証可能な最小構成に絞ります。

## 3. スコープ定義: やること (In-Scope)

### ① 認証・セキュリティ機能

- Clerkを用いたログイン/ログアウト画面。
- 認証されたユーザーのみが管理画面にアクセスできるアクセス制御。
- backend APIはClerk JWTを検証してから設定/通話履歴を返す。

### ② AI架電・受電コア機能 (backend)

- Twilio経由の指定番号への発信、または着信の受け付け (既存)。
- OpenAI Realtime APIを活用した、低遅延の音声対話の実行 (既存)。
- ※既存実装済みのコードベースをそのまま流用・稼働させる。

### ③ データ記録・分析機能

通話終了後、AIに通話内容を要約させ、以下のデータをFirestoreに保存する。

- 日時、電話番号、通話ステータス (完了、エラー等)
- 通話のテキスト要約
- **再架電フラグ (人間によるフォローアップが必要かどうか)**

FirestoreのデータをGoogle Sheetsへ自動転記する (既存機能の活用)。

### ④ 最低限の管理画面 (React UI)

- **通話履歴一覧画面**: Firestoreからデータを取得し、「電話番号」「日時」「要約」「再架電フラグ」をリスト表示するだけのシンプルな画面。
- **AI設定画面**: 以下の2つのテキストを入力し、Firestoreに保存するフォーム画面。
  - システムプロンプト (AIの役割、口調、ルールのテキスト)
  - RAG用ナレッジデータ (**Markdown形式のテキスト直書きのみ**)

通話開始時に、backendはFirestoreから上記の設定を読み出してOpenAI Realtimeセッションへ反映する。

## 4. スコープ外定義: やらないこと (Out-of-Scope)

PoCの期間・予算 (20万円想定の稼働) を守るため、以下の機能は本MVPでは明確に実装対象外とします。

| 項目 | 理由 |
| --- | --- |
| ノードベースのコールフロー構築エディタ | システムプロンプト1枚で代替 |
| ファイルアップロードRAG (PDF/PowerPoint等) | Markdownテキストの直接入力で代替 |
| ベクトル化・チャンク化・検索インデックス | Markdown全文をプロンプトに同梱して代替 |
| 高度なCRM/SFA連携 (Salesforce等) | スプレッドシート/CSVを手動活用 |
| チャットツール連携 (Slack / Teams通知) | エラー検知通知は対象外 |
| 独自の音声チューニング・疑似STS | OpenAI APIの仕様に依存 |
| リアルタイムの有人転送 (ホットトランスファー) | 「再架電フラグ」+ 人間架電で代替 |
| 発信リストの高度な管理・自動スケジューリング | スプレッドシート手動運用で代替 |
| backend のTypeScript化 | 既存JS実装を流用 |

## 6. 完了条件 (PoC受け入れ条件)

- 認証されたオペレーターがClerk経由でログインできる。
- 050番号への着信でAI受付が応答し、通話ログがFirestore + Sheetsに保存される。
- 管理画面で通話一覧 (電話番号、日時、要約、再架電フラグ) を確認できる。
- 管理画面でシステムプロンプトとMarkdownナレッジを編集して保存できる。
- 編集した設定が次回通話以降のAI応答に反映される。
- 既存の署名検証・プライバシーログ無効化・監査ログは引き続き機能する。
