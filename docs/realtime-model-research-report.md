# Realtimeモデル比較研究報告書

- 作成日: 2026-05-10
- 対象: Cor.株式会社の日本向け音声AI受付基盤
- 比較対象: `gpt-realtime-1.5`, `gpt-realtime-2`
- 関連ログ: `docs/realtime-model-benchmarks/2026-05-10-local.md`

## 要旨

現時点の結論は、Cor.株式会社の音声AI受付システムでは `gpt-realtime-2` を第一候補、かつ既定値にする判断が妥当である。

ただし、「全条件で `gpt-realtime-2` が明確に上」とは断定しない。今回の自社実測は Realtime WebSocket 接続と GA `session.update` 受理までの低リスクな疎通ベンチマークであり、実通話品質、固有名詞確認、tool selection、長時間会話の保持、割り込み復帰まではまだ測っていない。

研究判断としては次の整理が正確である。

- このシステムの主用途では `gpt-realtime-2` が優位。
- 単純、短時間、固定フロー、低推論、低変更リスクの用途では `gpt-realtime-1.5` が優位になり得る。
- 最終的な「明確に上」の証明には、接続ベンチマークに加えて、架空データだけを使った合成会話ベンチマークが必要。

## 根拠

OpenAI公式情報では、`gpt-realtime-2` は Realtime 音声向けの推論モデルであり、設定可能な reasoning effort、強い指示追従、より信頼できる tool use、128,000 context window を持つモデルとして位置づけられている。

Realtime prompting guide では、`gpt-realtime-2` を使う場合、単純な音声botではなく推論する音声エージェントとしてpromptを設計し、`reasoning.effort` は `low` から始めることが推奨されている。

一方、`gpt-realtime-1.5` は高速で信頼できる非推論の speech-to-speech モデルとして位置づけられており、短く単純な会話や、既存フローの変更リスクを避けたい場面では選択肢として残すべきである。

## 自社実測結果

2026-05-10の接続ベンチマークでは、両モデルとも 3/3 で Realtime 接続と `session.update` 受理に成功した。

| Model | OK | Connect median ms | Session updated median ms |
| --- | ---: | ---: | ---: |
| `gpt-realtime-1.5` | 3/3 | 1458 | 1693 |
| `gpt-realtime-2` | 3/3 | 619 | 870 |

この結果は、少なくとも現在のCor.開発環境では `gpt-realtime-2` が接続確立と `session.update` 受理までの測定で不利ではなく、むしろ速かったことを示す。

ただし、この数値は接続・設定受理だけを測ったものであり、ユーザー発話からAI音声応答までの総合レイテンシ、会話品質、通話単価を直接示すものではない。

## `gpt-realtime-2` が優れている条件

Cor.株式会社のAI受付では、以下の条件で `gpt-realtime-2` を優先する。

- 氏名、会社名、電話番号、予約日時、問い合わせ分類など、聞き取ったentityの保持と確認が重要。
- FAQ、予約確認、CRM参照、有人引き継ぎなど、tool selectionの誤りが運用品質に直結する。
- 通話が数分以上に伸び、前半の情報、訂正履歴、確認済み/未確認状態を保持する必要がある。
- 相手の言い直し、割り込み、曖昧な依頼から自然に復帰したい。
- 会社別、業種別、導入先別の受付ルールが増え、promptやナレッジが大きくなる。
- 単なる一問一答ではなく、確認、分岐、保留、エスカレーションの判断が必要。

このシステムは、最終的に「一次受付」「折り返し要否判断」「ナレッジ参照」「有人引き継ぎ」「通話ログ化」を扱うため、設計思想は `gpt-realtime-2` と合っている。

## `gpt-realtime-1.5` が優れている条件

`gpt-realtime-1.5` は以下の条件では引き続き有力である。

- 通話が短く、ほぼ固定文言の案内で終わる。
- tool callがない、または軽い読み取りだけで、推論や複雑な分岐が不要。
- 既存の1.5向けpromptと運用結果が十分に安定しており、モデル変更による挙動差を避けたい。
- latency SLOが極端に厳しく、`reasoning.effort` 由来の遅延・出力トークン増加を許容できない。
- 長いコンテキスト、厳密な状態保持、複雑なentity確認が不要。
- A/Bテストで `gpt-realtime-2` の会話品質改善が確認できず、コストまたは変更リスクのほうが大きい。

このため、研究・プロダクト方針としては `gpt-realtime-2` への全面固定ではなく、用途別に `REALTIME_MODEL` と `REALTIME_REASONING_EFFORT` を切り替え可能な設計を維持する。

## 判定マトリクス

| 評価軸 | 1.5が有利 | 2が有利 |
| --- | --- | --- |
| 短い固定受付 | 変更リスクが低い | 過剰な場合がある |
| 固有名詞・氏名確認 | 単純な復唱なら可 | 複雑な訂正や保持に強い |
| tool selection | 軽い分岐なら可 | 複数toolや確認境界に強い |
| 長時間会話 | コンテキスト制約が出やすい | 128K contextで有利 |
| promptの複雑化 | 競合指示に弱くなり得る | 再設計すれば有利 |
| 遅延 | 単純ケースで有利になり得る | 今回の接続実測では不利なし |
| 運用変更リスク | 既存安定運用では有利 | 移行テストが必要 |
| 今後の拡張性 | 限定的 | RAG、CRM、有人引き継ぎで有利 |

## Cor.研究対象として残すべき調査

次の研究ログを残すと、WellAI以外の提携、自社プロダクト化、業界別テンプレート展開に再利用できる。

1. 接続ベンチマーク
   - 既に実施済み。
   - `connectMs`, `sessionUpdatedMs`, 成功率、エラー内容を記録する。

2. 合成会話ベンチマーク
   - 実顧客データを使わず、架空会社、架空氏名、架空電話番号風ダミー値だけを使う。
   - 氏名確認、電話番号確認、希望日時、問い合わせ分類、聞き返し、言い直しを評価する。

3. tool selectionベンチマーク
   - FAQ参照、予約照会、有人引き継ぎ、折り返し登録などの架空toolで評価する。
   - 誤tool call、確認不足、不要なtool callを失敗として数える。

4. 長時間会話ベンチマーク
   - 会話の前半で得た情報を後半まで保持できるかを測る。
   - 訂正された情報を古い値で上書きしないかを確認する。

5. 音声体感評価
   - 実電話ではなく合成音声または社内テスト通話で、割り込み、間、聞き返し、自然さを評価する。
   - transcriptや録音を残す場合は、個人情報・顧客情報を含めない。

## NDA・機密情報境界

この研究報告は、OpenAI公式公開情報、Cor.が作成した汎用コード、Cor.の汎用ベンチマーク結果だけに基づく。

含めてよいもの:

- OpenAI公開ドキュメント/ブログの一般情報。
- Cor.の汎用ベンチマークコードと集計値。
- 架空データだけで作る評価ケース。
- モデル名、設定、成功率、遅延、エラー分類。

含めてはいけないもの:

- WellAIの実プロンプト、会話設計、業務ルール。
- 実通話 transcript、録音、要約、電話番号。
- 顧客固有情報、実会社名、実担当者名、予約番号。
- NDA資料やNDAミーティングから派生した文言。

## 推奨方針

短期方針:

- 本リポジトリの既定は `gpt-realtime-2` + `REALTIME_REASONING_EFFORT=low` のまま維持する。
- `REALTIME_MODEL` により `gpt-realtime-1.5` へ戻せる逃げ道は残す。
- 既存の接続ベンチマークをCI外の手動研究ログとして継続する。

中期方針:

- 合成会話ベンチマークを追加し、`gpt-realtime-1.5` と `gpt-realtime-2` の会話品質を同一条件で比較する。
- 受付用途では、entity capture、確認境界、tool selection、有人引き継ぎの成功率を主指標にする。
- 遅延は接続時間ではなく、ユーザー発話終了からAI音声開始までを別途測る。

最終判断:

- 受付・RAG・CRM・有人引き継ぎを含むCor.の将来システムでは `gpt-realtime-2` が本命。
- 単純な電話案内、短時間の固定受付、既存安定運用の維持では `gpt-realtime-1.5` も残す。
- 研究報告としては「2が明確に上」ではなく、「Cor.の目指す受付システムでは2が優位。1.5は単純・低変更リスク用途で比較対象として残す」と表現するのが正確。
