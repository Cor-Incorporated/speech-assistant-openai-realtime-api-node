# ADR 0008: 電話応答練習システムの分離とDTMF振り分けゲートウェイ

- ステータス: 採用
- 日付: 2026-07-15
- 対象: 電話応答練習システム（AI顧客役＋評価エンジン）の実装場所、着信振り分け、Emotion Logic連携の責務境界

## 背景

アルバイト向け電話応答練習システム（AIが顧客役を演じ、練習者の応対を「内容×感情×話速」の3系統で評価するSaaS構想）の企画・要件定義が承認されている。要件定義書は本リポジトリを音声基盤として流用する前提で書かれている。

一方、練習システムには本リポジトリ（受付システム）と根本的に異なる要件がある。

- 練習者音声の**録音**と外部感情解析API（Emotion Logic）への送信（受付システムは録音を持たず、[セキュリティ方針](../security-privacy-logging.md)も録音を保存しない前提）
- マルチテナント・課金（SaaS外販）
- 評価エンジン・シナリオ管理などの大規模な新規機能

また、Twilioの050番号は現在1つのみで、テスト段階で追加番号を発行するのは費用対効果が悪い。

## 決定

### 1. 練習システムは別リポジトリ + 別GCPプロジェクトとする

- 本リポジトリを**フォーク**して新リポジトリを作成し、専用GCPプロジェクトへデプロイする。
- 評価エンジン（話速自前計算 + 文字起こし×LLM評価 + Emotion Logic感情解析の3系統統合）、録音/音声tee、μ-law→PCM変換、EMLO Docker運用は**すべて新リポジトリのスコープ**。
- 引き継ぎ資料: [practice-system-handover.md](../practice-system-handover.md)、[emotion-logic-api-notes.md](../emotion-logic-api-notes.md)

### 2. 本リポジトリの責務はDTMF振り分けゲートウェイのみ

1つの050番号で受付と練習の両方を受けるため、着信時にDTMF（プッシュ信号）で振り分ける。

- `/incoming-call` で `<Gather input="dtmf">` を先行させ、DTMF `5`（終端 `#`）が入力されたら練習システムのCloud Run URLへ `<Redirect>` する（通話ごと引き渡し。プロジェクト跨ぎで動作する）。
- 無入力・タイムアウト・その他の入力は、従来どおり `<Connect><Stream>` のAI受付フローへ進む。一般の発信者の体験を変えないことを最優先とする。
- フィーチャーフラグ `DTMF_GATEWAY_ENABLED`（既定 false）で制御し、練習システム稼働まで無効とする。
- 詳細設計: [dtmf-gateway-design.md](../dtmf-gateway-design.md)

### 3. 本リポジトリに録音・音声tee・Emotion Logic連携は追加しない

受付システムの「音声を保存しない」性質を維持する。Emotion LogicのAPI仕様調査結果は引き継ぎ資料として本リポジトリの `docs/` に置くが、実装は新リポジトリで行う。

## 理由

- 番号1つでの同居を実現しつつ、受付システムのコードベース・プライバシー特性・課金を練習SaaSから隔離できる
- 練習システムはSaaS化でテナント分離・課金が必要になり、早期分離のほうが移行コストが小さい
- `<Redirect>` はTwilio標準機能であり、ゲートウェイ側の実装は小さく保てる

## 影響

- 関連issue: DTMFゲートウェイ実装（Wave E1）、新リポジトリ立ち上げ引き継ぎ（Wave E2）
- 将来、練習システムが専用番号を持つ段階になれば、ゲートウェイのDTMF分岐は削除できる（フラグOFFで即時退役可能）
